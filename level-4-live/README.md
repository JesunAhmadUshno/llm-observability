# Level 4 Live: real-traffic observation

Levels 1 to 3 run on simulated traffic, and the main README said so:
no real LLM traffic was observed. This level fixes that sentence with
a measured window of real model calls, labelled for exactly what it
is.

## What ran

- Host: BlackBoxV3 (a personal fleet machine, Intel i5-8400, 6 cores,
  no GPU). BlackBoxV2 was the planned host; it was unreachable on
  2026-11-15 (absent from the tailnet device list, SSH and HTTP probes
  unanswered), so the run moved to the fleet's other always-on Linux
  node. The substitution is recorded here, not hidden.
- Model server: llama.cpp b12418 (llama-server) serving
  Qwen2.5-0.5B-Instruct, GGUF Q4_K_M, on 127.0.0.1:18080, CPU only.
  Model file SHA-256:
  74a4da8c9fdbcd15bd1f6d01d621410d31c6fc00986f5eb687824e7b93d7a9db.
- Service: server.py in this folder, on 127.0.0.1:18081. Each /ask
  call builds a document question from corpus.json, calls the model
  server, times the call with a wall clock, and persists the record
  and its trace spans through the Level 2 LogStore.
- Workload: client.py in this folder asked the questions in a seeded
  shuffled rotation with jittered gaps of 15 to 27 seconds.

## Honest labels

- The completions are real: generated by the model at request time.
  Token counts are the model server's own usage counts.
- The traffic is program-driven: a shipped client asking genuine
  questions about the bundled documents (excerpts of this repo's own
  documentation). It is not organic user traffic, not production
  traffic, and not production scale.
- Cost is 0 by construction: the model is self-hosted, so the live
  price table carries zero rates. That is an accounting statement,
  not a price.
- The answer check is mechanical: the completion contains the
  expected answer string from the document (case-insensitive). It
  measures whether the model surfaced the answer in the document it
  was given. It is not a human quality judgement.

## Files

| Path | What it holds |
| --- | --- |
| corpus.json | 12 documents excerpted from this repo, 24 questions with expected answers |
| live.py | Model client, wall clock, the recorder that writes records and spans |
| server.py | The instrumented HTTP service (POST /ask, GET /health) |
| client.py | The workload driver that generated the window |
| analyze.py | Turns the store into results_live.json with the repo's own statistics |
| store_live.jsonl | The captured store: every record and span from the window |
| results_live.json | The measured summary of the window |

## Reproduce the analysis

The window itself cannot be re-run byte for byte (it is a real
observation, not a seeded simulation), but the analysis can:

```text
python3 level-4-live/analyze.py --store level-4-live/store_live.jsonl \
    --out level-4-live/results_live.json --host-label BlackBoxV3 \
    --model-sha256 74a4da8c9fdbcd15bd1f6d01d621410d31c6fc00986f5eb687824e7b93d7a9db \
    --runtime "llama.cpp b12418, llama-server, CPU, 6 threads"
```

## Results (measured 2026-11-15)

Window: 2026-11-15 16:35:41 to 18:33:36 UTC (7,074.7 s, about
1 h 58 min), 340 requests, cross-checked against the client log
(340 attempts, all ok).

| Measure | Value |
| --- | --- |
| Errors | 0 of 340 (error rate 0.0) |
| Latency mean / p50 / p95 / p99 | 304 ms / 287 ms / 653 ms / 718 ms |
| Latency min / max | 94 ms / 772 ms |
| Tokens (server usage counts) | 44,829 prompt + 3,627 completion = 48,456 |
| Answer check | 255/340 passed (0.75); 18 of 24 questions passed every attempt, 6 failed every attempt |
| Drift, first half vs second half | latency PSI 0.033, tokens PSI 0.001, no alerts |

The finding that matters is in the answer check's per-question
split: the failures are mostly phrasing misses against the
document's exact string, plus one polarity slip, so 0.75 is
exact-phrase recall, not semantic accuracy. Full record:
results_live.json. Write-up: REPORT.md, "Live observation
(2026-11-15)".
